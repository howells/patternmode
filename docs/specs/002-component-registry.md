# Spec 002 — Component Registry: Vendoring @patternmode/\* via shadcn

**Status:** Implemented
**Date:** 2026-07-10
**Repo:** `~/Sites/patternmode` (existing monorepo)
**Builds on:** Spec 001 (`docs/specs/001-patternmode-theme.md`), which shipped the theme-only registry and explicitly deferred component distribution. See that spec's Amendments section for what changed underneath it.

## Problem

Spec 001 shipped `@patternmode/theme` — tokens only, deliberately. But `@patternmode/*` components (Aperto, Deck, Stacksheet, Swatch, Tags, …) are npm packages, and npm is the wrong distribution shape for a design-system component: consumers can't see or edit the source without ejecting, and every future change is an opaque version bump. shadcn's registry model — CLI-installed, vendored, consumer-owned source — is the better fit, and Spec 001 already built the hosting mechanism (`apps/web/public/r`, a real domain, the `shadcn build` pipeline). This spec extends that pipeline to vendor the ten `@patternmode/*` component packages (plus the two shared libraries they depend on, `system` and `motion`) as registry items, alongside the existing theme.

## Architecture

```
packages/<pkg>/src/**                     (hand-written source, the real npm package)
        │
        ▼
scripts/build-registry.mjs                (generator — run from packages/theme)
  1. rewrite internal bare specifiers      (@patternmode/*, @howells/motion → @/… aliases)
  2. strip `declare global` blocks         (stacksheet only — see Defects)
  3. prepend provenance comment            (`// vendored from <pkg>@<version> — …`)
  4. inline / attach CSS per package style (A / B / C — see Vendoring model)
  5. split deps → npm `dependencies` vs.   (internal deps become full-URL registryDependencies)
     `registryDependencies`
        │
        ▼
packages/theme/.staging/                  (staged file tree + registry.json manifest)
        │  `shadcn build .staging/registry.json --output dist/registry`
        ▼
packages/theme/dist/registry/*.json       (14 registry items: theme, font-inter, system, motion,
                                            + 10 components)
        │
        ├─▶ apps/web/scripts/copy-registry.mjs  (runs before `next build` / `next dev`)
        │        ▼
        │   apps/web/public/r/*.json
        │        ▼
        │   Vercel serves apps/web  →  https://patternmode.com/r/{name}.json
        │
        └─▶ apps/preview/scripts/sync-registry.mjs  (loopback re-vendor — see Preview honesty)
```

The generator (`scripts/build-registry.mjs`) is shared, repo-root code — not inside `packages/theme` — because it reads every component package's `src/` directly. `packages/theme` stays the _hand-authored_ half of the registry: `theme` (`registry:theme`, oklch `cssVars.light`/`.dark` plus `font-sans`/`font-mono` in `cssVars.theme`, base CSS compiled from `theme.css`) and `font-inter` (`registry:item`, bundling Inter Variable through `@fontsource-variable/inter`; its bare-specifier `@import "@fontsource-variable/inter/…"` assumes a bundler-aware CSS pipeline — webpack/Turbopack/postcss-import — which holds for every Next.js/Tailwind-v4 consumer this registry targets). The other 12 items — `system` and `motion` as `registry:lib`, and the 10 component packages as `registry:component` — are generated by vendoring each package's actual source, not hand-copied.

`packages/theme` is `private: true` and devDepends on every component package as `workspace:*`, purely to wire Turborepo's dependency graph: a source change in any `@patternmode/*` package correctly invalidates the theme's build cache (`^build`), so `pnpm turbo run build --filter=@patternmode/theme` never serves a stale registry.

## Vendoring model

Each generated item is built from real package source with these transforms applied in order:

1. **Specifier rewriting.** Every internal bare specifier is rewritten to the `@/`-aliased path a consumer's vendored copy will actually live at. This covers the three documented cross-package runtime imports, plus (generated from the same package allowlists) every package's _own_ specifier, so self-referential imports inside JSDoc examples (e.g. a `@patternmode/aperto` usage snippet inside the aperto package itself) also point at the vendored location instead of a bare npm specifier the consumer doesn't have.

   | Bare specifier                                      | Vendored target                        |
   | --------------------------------------------------- | -------------------------------------- |
   | `@patternmode/system`                               | `@/lib/patternmode/system`             |
   | `@howells/motion`                                   | `@/lib/patternmode/motion`             |
   | `@patternmode/scrollframe`                          | `@/components/patternmode/scrollframe` |
   | `@patternmode/<component>` (all 10, self-reference) | `@/components/patternmode/<component>` |

   A guardrail (`assertNoInternalSpecifiers`) scans every staged file afterward and throws if any `@patternmode/…` or `@howells/…` specifier survived — an unmapped internal import fails the build loudly instead of shipping broken source. `scripts/build-registry.mjs --check` re-asserts this against the _emitted_ item JSON (`checkNoLeaks`) as a second, independent gate.

2. **Provenance.** Every staged file gets a leading `// vendored from <npm-name>@<version> — generated by scripts/build-registry.mjs; do not hand-edit.` comment (inserted after a leading `"use client";` directive, if present), and every item carries `meta.sourceVersion` — the same `<npm-name>@<version>` string, as a JSON field rather than a comment.

3. **CSS handling — three styles, hard-coded per package (never sniffed):**

   | Style | Packages                                                 | Mechanism                                                                                                                                                                                                         |
   | ----- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | A     | briolette, deck, halo, scrollframe, status, swatch, tags | `src/styles.css` is parsed and compiled into the item's `css` field (same mechanism as the theme's base CSS) — the shadcn CLI merges it into the consumer's global stylesheet automatically.                      |
   | B     | aperto, parquet                                          | `styles.css` ships as a `registry:file` entry, and `import "./styles.css";` is injected into the vendored `index.ts`. Uses `@reference`/`@apply`, so the item's `docs` field states `"Requires Tailwind CSS v4."` |
   | C     | stacksheet                                               | No CSS at all — the component is styled with inline utility classes only.                                                                                                                                         |

4. **Ambient-global stripping.** `STRIP_GLOBAL_DECLARATIONS` (currently `{"stacksheet"}`) lists packages whose vendored source has every top-level `declare global { … }` block removed during staging (plus any `//` comment lines directly above it). See Defects found & fixed for why. The build throws if a listed package's `src/` no longer contains any such block, so a future stacksheet refactor can't silently change staging semantics — the entry has to be deliberately removed.

5. **Dependency splitting.** A package's `dependencies` are split into external npm `dependencies` (as `name@range` strings, with `catalog:`/`workspace:*` ranges resolved to concrete semver via `pnpm-workspace.yaml`) and `registryDependencies`. Internal dependencies (anything in `INTERNAL_REGISTRY`: `motion`, `scrollframe`, `system`) become **full URLs** — `${REGISTRY_BASE_URL}/r/<name>.json` — rather than `@patternmode/<name>` namespace references. This is deliberate: a raw-URL install (`shadcn add https://patternmode.com/r/theme.json`) has no `components.json` `registries` entry to resolve a namespace reference against, so a namespace-form `registryDependencies` entry would silently break that install path. Full URLs work for both.

6. **Base URL resolution and fail-fast.** `REGISTRY_BASE_URL` drives every baked URL (registry homepage, `registryDependencies`, the theme's `font-inter` reference). If unset, the generator defaults to `http://localhost:3000` with a warning — _unless_ `VERCEL` is set, in which case it throws immediately: baking `localhost` into a production registry build is refused outright rather than silently shipping a broken registry.

## Token contract

Component packages read the **standard shadcn theme variable vocabulary** — not a bespoke `@patternmode/*` or `--sc-*` namespace — with each component's original hex value preserved as the `var(...)` fallback. This was a rename from the project's earlier ad hoc token names, shipped as a `minor` version bump (`briolette`, `halo`, `scrollframe`, `status`, `swatch`, `tags`) because the old names were public theming hooks consumers may have set directly:

| Old name         | New name                                                                     |
| ---------------- | ---------------------------------------------------------------------------- |
| `--ink`          | `--foreground`                                                               |
| `--muted`        | `--muted-foreground`                                                         |
| `--accent`       | `--ring`                                                                     |
| `--accent-soft`  | `--accent`                                                                   |
| `--surface`      | `--card`                                                                     |
| `--surface-soft` | `--muted`                                                                    |
| `--border-soft`  | `--border-subtle` (patternmode extension — opt-in, not a stock shadcn token) |
| `--quiet`        | `--muted-foreground`                                                         |

Nothing renders differently out of the box — the hex fallbacks are unchanged — but a consumer already using shadcn's own theme variables now themes these components automatically, with no bespoke overrides required.

`scripts/check-tokens.mjs` (`pnpm check:tokens`, part of `pnpm check`) enforces this vocabulary: it scans every `var(--name)` reference in each package's CSS (and quoted `"--name":` inline-style keys in its `src/**/*.{ts,tsx}`) and fails if `--name` isn't in one of:

- the canonical shadcn token set (`--background`, `--ring`, `--sidebar-*`, …) plus Tailwind's own custom properties (`font-*`, `shadow-*`, `spacing`, `tw-*`) and the `border-subtle` extension,
- `patternmode-*` (any patternmode-namespaced extension),
- a name the _same_ package defines itself (its own CSS declarations or inline-style keys — e.g. deck's `--deck-perspective`),
- runtime-provided (`available-height`, `anchor-width` — injected by Base UI anchor positioning for tags' popover; never defined in CSS), or
- consumer-tunable (`aperto-radius`, `aperto-caption-allowance`, `aperto-expanded-width` — documented knobs referenced with fallbacks but intentionally never defined by the package; consumers set them to override).

## Hosting & consumption

`apps/web/scripts/copy-registry.mjs` copies `packages/theme/dist/registry/*.json` into `apps/web/public/r/` before every `next build`/`next dev` (fails loudly if the source is empty, pointing at the `turbo run build --filter=@patternmode/theme` command to run first). Vercel serves `apps/web` at the production domain **https://patternmode.com**, so the registry rides that deployment's existing hosting — no separate service. `REGISTRY_BASE_URL` is set as a Vercel environment variable for both the production and preview environments, so preview deployments bake their own preview URL into `registryDependencies` rather than pointing at production.

Two ways to consume an item, both exercised and both supported:

**Namespace** (the primary UX — add once, then reference by short name):

```json
// components.json
{ "registries": { "@patternmode": "https://patternmode.com/r/{name}.json" } }
```

```bash
npx shadcn add @patternmode/theme @patternmode/swatch
```

**Raw URL** (no `components.json` config needed):

```bash
npx shadcn add https://patternmode.com/r/theme.json
```

**Dual-channel distribution.** `@patternmode/*` packages are published to npm _and_ served from this registry — deliberately two different contracts, not two copies of the same thing:

- **npm** = a managed, versioned dependency. Semver updates flow through the consumer's package manager; the consumer never sees or edits the source.
- **registry** = vendored source the consumer owns outright. It's frozen at install time — no lockfile entry updates it — and editing it is expected. Picking up an upstream change means explicitly re-running `shadcn add <item> --overwrite`.

**Known caveat.** The shadcn CLI strips a file's leading provenance comment on `add` for any file that doesn't start with a `"use client"` directive (the transform treats a detached leading comment as disposable). The comment is cosmetic; `meta.sourceVersion` in the registry item JSON is the authoritative record of what was vendored, since it's a structured field the CLI doesn't touch. `apps/preview`'s sync step actively repairs the stripped comment for local files (see below) purely for local readability — it isn't required for correctness.

## Preview honesty mechanism

`apps/preview` is a stock shadcn app whose vendored `components/patternmode/**` and `lib/patternmode/**` are never hand-edited — they're re-vendored from the freshly built registry on every `pnpm dev` and `pnpm build`, via `apps/preview/scripts/sync-registry.mjs`. The one preview-owned app file shadcn still rewrites is `app/globals.css` — the theme item's cssVars/css merge; `app/layout.tsx` is left alone, since font wiring only ever fired for `registry:font` items and `font-inter` is now a plain `registry:item`. Font loading therefore arrives through that same globals.css merge, so the preview consumes `@fontsource-variable/inter` exactly as any external consumer does — no `next/font` anywhere. The sync step:

1. **Rebuild** `packages/theme/dist/registry` by running `scripts/build-registry.mjs` with `REGISTRY_BASE_URL=http://127.0.0.1:4787`.
2. **Serve** that directory over a throwaway loopback HTTP server on `127.0.0.1:4787` (fails with a clear message if the port is already bound).
3. **Install**: `shadcn add --yes --overwrite @patternmode/theme @patternmode/swatch @patternmode/deck @patternmode/tags @patternmode/stacksheet` against the loopback registry, targeting `apps/preview`. `registryDependencies` (`system`, `motion`, `scrollframe`) are pulled in transitively.
4. **Repair**: re-insert the provenance comment shadcn's `add` transform stripped (reading it back out of the built item JSON's `content` field, which is unaffected), strip the vendored `declare global { var process … }` block if the _served_ item still carries one — a defensive no-op today, since step 1 already stripped it at generation time (see Defects) — and drop the duplicate top-level `@property` blocks shadcn's css merge re-appends on every run (it dedupes `@import`s but appends non-empty at-rules unconditionally).

Because this runs on _every_ `dev`/`build`, a generator regression — a bad specifier rewrite, a missing CSS style entry, a broken dependency split — fails the preview build immediately instead of drifting silently until someone runs a stock consumption test by hand.

## Defects found & fixed

Two defects surfaced during the acceptance pass and were fixed in the generator/source, not papered over downstream:

1. **`shadcn update-css` crashed on a self-referential `@theme inline` map.** `packages/theme/registry/theme/theme.css` used to ship

   ```css
   @theme inline {
     --shadow-xs: var(--shadow-xs);
     --shadow-sm: var(--shadow-sm);
     /* … */
   }
   ```

   mapping the shadow scale onto itself so Tailwind v4 would pick the tokens up as utilities. shadcn 4.11–4.13's `update-css` step can't parse a self-referential custom property and aborts the whole `shadcn add` with `Unknown word var`. **Fix:** the block was deleted outright — shadcn's current `update-css` already auto-derives the identical `@theme inline` mapping from any `shadow-*`/`font-*` key present in `cssVars`, so the output is byte-identical without it. `apps/preview/scripts/sync-registry.mjs` still carries a `sanitizeRegistryItem()` step that strips a `css["@theme inline"]` key from the served theme item as a defensive no-op — it becomes inert automatically if the source ever regresses.

2. **Stacksheet's ambient globals collided with `@types/node`.** Stacksheet ships a minimal `declare global { var process: … }` (so it typechecks in browser-only contexts without Node's ambient types) plus a `CloseWatcher` declaration. Vendored verbatim into a consumer Next.js app — where `@types/node` is almost always in scope transitively — the `process` declaration collides with `@types/node`'s own and TypeScript fails with `TS2403`, unfixable from the consumer's `tsconfig.json`. **Fix:** `STRIP_GLOBAL_DECLARATIONS` in `scripts/build-registry.mjs` removes every top-level `declare global` block from stacksheet's staged source. The blocks are type-only, so runtime behavior is unchanged; the build fails loudly if stacksheet ever stops shipping one, so the strip step can't quietly go stale.

## Update/versioning story

There is no independent registry versioning scheme today (no `/r/v1/theme.json`-style paths) — items are served unversioned at `/r/{name}.json`, always reflecting whatever `packages/*/src` looked like at the last `shadcn build`. Two update mechanisms exist, tracking Spec 001's stance for the theme and extending it to components:

- **Registry channel:** re-run `npx shadcn add <item> --overwrite` (the CLI prompts before overwriting local edits). `apps/preview`'s `pnpm sync` does this automatically for its five vendored items on every dev/build.
- **npm channel:** unaffected by the registry — component packages still version via Changesets (`pnpm version-packages`, `pnpm publish:packages`) whenever their public API changes, independent of when the registry is next rebuilt.

`meta.sourceVersion` on every generated item is the durable record of what was vendored (`<npm-name>@<version>`), readable even after the CLI strips the human-facing provenance comment — this is what makes "what version is this vendored copy actually from" answerable without re-diffing source. A future versioned-path scheme (`/r/v1/…`) can be added later without breaking the unversioned URLs any existing consumer already installed from.
